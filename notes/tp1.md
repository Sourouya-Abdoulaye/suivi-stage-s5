# 3. Le modèle Entreprise 
## 3.1 La spécification Justifications des choix — Modele Entreprise

### Unicite : sur les champs nom,ville 
Une même entrep peut avoir des agences dans plusieurs villes
(Ecobank à Sokode ≠ Ecobank à Lome). Le couple (nom, ville) identifie
une entite locale sans ambiguïte, sans imposer un identifiant externe.


### L’adresse mail doit etre de type `EmailField` au lieu de `CharField`
pour facliter la validation d'email, (rejet d'un email mal forme lors de la saisie) et permet d'utiliser `django.core.mail` directement sans conversion manuelle.


### Tye Choice pour le secteur 
Garantit la coherence : pas de "IT", "Technologi","Technologie", "tech" pour la même chose.
Coût : ajouter un secteur exige une migration.Mais En pratique la liste
evolue rarement, donc selons moi le gain l'emporte sur l'inconvenient.


### `__str__`
La dernière phrase du secretariat ("on veut la reconnaître tout de suite, sans avoir à cliquer") ne parle pas d'un champ mais de l'affichage de l'objet . lors de l'affichage c'est le `__str__` qui   est appele par Django dans l'admin, le shell et les templates sans lui, on verrait l'objet sous cette forme  `<Entreprise object (1)>` on ne sait pas c'est qu'elle entreprise Mais avec `__str__` on peut avoir quelque chose comme ca ` <Entreprise: sourouya (sokode)>` dans le shell.


## 3.2 Migrations
### a.la contrainte qui interdit les doublons et son nom ?
CONSTRAINT "nom_ville_unique" UNIQUE ("nom", "ville") 
le nom est: la Constrainte d'uniciter

### b. La colonne sans equivalent

La colonne **`id`** (`biginteger NOT NULL PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY`).
Elle sort de l'`AutoField` (champ automatique) implicite, Django ajoute automatiquement un champ nommer `id` dès qu'aucun champ n'est declarer `primary_key=True`.



### c. Modifier `max_length` et relancer

Après `makemigrations`, il y a **2 fichiers** dans `stages/migrations/` 
- `0001_initial.py`
- `0002_alter_entreprise_nom.py`

Pour revenir en arrière on tape : `uv run manage.py migrate nom_app nom_migration`
ex: `uv run manage.py migrate stages 0001`

## 6. Le depôt git
Ce qui manque dans .gitignore c'est db.sqlite3

a. Pourquoi ne se commite-t-elle pas ?
C'est la base de donnees : un fichier binaire d'etat, pas du code source.
La source de verite est dans les migrations (qui reconstruisent la structure)
et les donnees d'exemple (qu'on peut re-saisir). Commiter db.sqlite3
creerait des conflits à chaque migrate et exposerait des donnees reelles.

b. Les deux fichiers à commiter
pyproject.toml : declare les dependances (Django, etc.) — c'est la recette.
uv.lock : verrouille les versions exactes de toutes les dependances —
c'est ce qui garantit que uv sync sur une autre machine installe
exactement les mêmes paquets.

Commits suggeres

initialisation du projet Django (suivi_stages) avec uv
,creation de modèle Entreprise avec unicite (nom, ville)
, declaration admin avec list_display et search_fields
,page liste des entreprises (vue, template, urls)
et ajout db.sqlite3 au .gitignore

## Restitution
1. Retrouver l'environnement sur une autre machine
git clone <url-du-depot>
cd suivi_stages
uv sync

uv sync va lire uv.lock et installe les versions exactement verrouillees.


2. Qui decide de la forme de la table ?
Le fichier de migration. C'est lui qui contient le SQL execute par migrate. models.py est la source de verite pour generer les migrations,
mais c'est le fichier de migration qui, une fois ecrit, decide de la forme reelle de la table en base.

3. Lire les erreurs de Django
Template manquant : la page d'erreur listait les chemins et dis
le nom du fichier ou son emplacement etait mauvais.
Contrainte d'unicite : le message citait les champs impliques
(Nom and Ville) on sait exactement quel couple est en conflit.
